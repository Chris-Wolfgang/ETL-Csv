# Security Policy

## Reporting a Vulnerability

If you discover a security vulnerability, please follow these steps:

1. **Do not** create a public issue on this repository.
2. In the top navigation of this repository, click the **Security** tab.
3. In the top right, click the **Report a vulnerability** button.
4. Fill out the provided form with:
   - A description of the vulnerability
   - Steps to reproduce the issue
   - Potential impact
   - Suggested fix (if you have one)

## Response Timeline

We will acknowledge your report within 48 hours and provide an estimated timeline for a fix.

## Thank You

Your help is greatly appreciated!
Responsible disclosure of security vulnerabilities helps protect our entire community.

## Release path & compromise scope

Facts a maintainer would need at 2am if the release identity is compromised. Generic incident-response steps (rotating credentials, revoking OAuth apps, publishing advisories, unlisting NuGet packages) are not duplicated here — GitHub's and NuGet's own docs update faster than a checked-in runbook.

- **Release path**: OIDC / NuGet Trusted Publishing via the SHA-pinned `NuGet/login` action (v1) in `.github/workflows/release.yaml`. The workflow mints an ephemeral push token per run via OIDC — the release path does not depend on a long-lived API key stored in GitHub secrets or on the NuGet account. During an incident, check the NuGet account for any long-lived API keys anyway (they can be created outside of CI) and delete anything you don't recognize.
- **Fallback**: none. If Trusted Publishing is compromised, the incident is at the GitHub-account level (the OIDC identity is `Chris-Wolfgang/ETL-Csv`).
- **Owner**: @Chris-Wolfgang.
- **Downstream consumers**: none known within the `Wolfgang.*` family — `Wolfgang.Etl.Csv` is a leaf extractor/loader implementation, not a dependency of the other ETL packages. Unknown external consumers may exist on NuGet.org.
- **Package coordinates for unlisting**: `Wolfgang.Etl.Csv` — https://www.nuget.org/packages/Wolfgang.Etl.Csv/ (single package).

## Verifying a release (provenance + SBOM)

Every release is published with two supply-chain artifacts so a consumer can prove that what they downloaded from NuGet was built from this repository, with no injection at any link (#71). Package **signing** (Authenticode / NuGet author signature) is not yet in place — it is tracked separately as #170, pending a code-signing certificate — so provenance + SBOM cover the chain in the meantime.

**1. SLSA build provenance** — every `.nupkg` carries a build-provenance attestation generated by `release.yaml` (`actions/attest-build-provenance`). Download the package (from NuGet or the GitHub Release) and verify it — substituting the version you downloaded for `0.3.0`:

```bash
gh attestation verify Wolfgang.Etl.Csv.0.3.0.nupkg --repo Chris-Wolfgang/ETL-Csv
```

A passing check proves the package was built by this repo's release workflow from the tagged commit — not repackaged or injected elsewhere.

**2. SBOM (CycloneDX)** — each GitHub Release attaches `Wolfgang.Etl.Csv.bom.json`, a CycloneDX software bill of materials listing the full (transitive) dependency graph. Feed it to any CycloneDX-aware scanner to audit dependencies and known CVEs — e.g.:

```bash
grype sbom:Wolfgang.Etl.Csv.bom.json          # vulnerability scan
# or import into Dependency-Track / OWASP tooling
```

Together the provenance answers **where and how** the package was built, and the SBOM answers **what is inside it** — the two halves of the supply chain.
